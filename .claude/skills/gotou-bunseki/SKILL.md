# gotou-bunseki — 1回で出し切る誤答分析

## なぜこのスキルがあるか

2026-11-22 の H24 電力 問11（ケーブルの充電容量）の分析では、解き方の核心が出てくるまでに学習者が3回聞き直す必要があった。

1. 写真と「わからなかった」に対して、応答しなかった。学習者が「分析は？」と催促した
2. 「C には相電圧」と**規則**で説明し、理由を「中性点（大地）」と書いて相電圧と対地電圧を同じものとして扱った。学習者は「相電圧？対地電圧？」と聞き返した
3. 学習者が「C が対地間の容量だから相電圧？」と自分で理由を立てて確かめに来た。ここでやっと、原理（I = ωC ×その C の両端の電圧）と、C の種類ごとの両端を示せた

3回の聞き直しは、どれも**最初の解説の穴**を学習者が埋めに来たもの。このスキルの目的は、その穴を最初の応答で埋めておくこと。学習者は、規則を覚えても次の問題で使えない。使えるのは「なぜそうなるか」が条件の違う問題でも成り立つ形で説明されたときだけ。

## 始める前に読むもの

- `mistakes/weak_points.md`：同じテーマや近いパターンの記録と改修履歴。効果を確かめていない対策を、確定した知識として繰り返さない（CLAUDE.md の 6）
- `data/records.json`：テーマ名や関連語で grep し、過去の誤答・memo・patch を見る。patch は当時の AI 解説なので、正しいとは限らない
- `notes/` と `data/concept-questions.json`：用語と記号をそろえるため

## 最初の応答に必ず入れるもの（この順番）

### 1. 誤答の再現
- 計算用紙や選んだ選択肢から、学習者がどう計算したかを1行ずつ書き起こす。写真の読み取りに自信がなければ、そう書く
- **誤答の数値を実際に計算して、選んだ選択肢と一致するか確かめる**（例：√3VωCV = 12.4 kV·A → 選択肢 (4) 12）。一致すれば診断が当たっている根拠になる。一致しなければ、診断を言い切らない
- 正解との差がどんな形か（√3 倍、2 倍、単位の 10³ など）を書く。差の形は、どこで間違えたかの手がかりになる

### 2. 原理（規則ではなく、いちばん一般的な式から）
- 「〜には相電圧を使う」のような規則で終わらせない。規則の元になる、いちばん一般的な関係を先に書く（例：**I = ωC ×その C の両端の電圧**）。規則は、その式に今回の条件を入れた結果として導く
- 学習者が「意味がわからない」と言った量（例：充電電流）は、物理的に何が起きているかで定義する（例：ケーブルは心線と大地を極板にしたコンデンサ。交流で充放電を繰り返すので、無負荷でも電流が流れる）
- 正しい数値の検算を、途中の値も含めて書く。数値は Python などで実際に計算する

### 3. 用語の区別（近い用語を先回りして分ける）
- 説明に出てくる用語のうち、**似た用語があるもの**を全部挙げ、定義を並べる。例：相電圧／対地電圧／線間電圧、作用静電容量／対地静電容量／線間静電容量
- 2つの量が同じ値になるときは、**同じになる条件と、違う値になる場面**を書く。「中性点（大地）」のように、括弧や「＝」で2つを同一視する書き方はしない
- 表にすると区別しやすい（量・両端または定義・使う値）

### 4. 崩れる条件（今回の規則が使えない類題）
- 今回の解き方が成り立たなくなる場面を、少なくとも2つ書く（例：Cs と Cm が別々に与えられる問題、非接地系の1線地絡）
- 学習者が立てそうな「半分だけ正しい理由」（例：「対地間だから相電圧」）を先に挙げ、どこで崩れるかを示す

### 5. 解くときの手順（3〜4行）
- 試験中に余白に書ける長さにする。最初の行は「何を確かめるか」にする（例：その C の両端を書く）
- 過去の記録に同じ種類の対策があり効いていなかったなら、それと違う手順にする。違う理由を1行書く

### 6. 過去記録との照合
- 関連する記録があれば `rec:日付/theme_id/attempt` で示す
- **似た場面の記録と、同じ原因とを分ける**。1件の誤答から「2回目」「同じところで間違えた」と断定しない（weak_points.md の位置づけの規則）

### 7. 確認問題（答えは書かない）
- 条件を変えた類題を1〜2問出す。今回の穴をそのまま突く形にする。例えば、答えの式では √3 が打ち消し合って穴が見えない問題なら、途中の量（電流）を問う
- 答えは書かない。学習者が答えたら採点する

### 8. 記録の提案
- `mistakes/weak_points.md` への記録を提案する（新しいパターンなら記録フォーマットで、既存なら改修履歴に1行）
- `data/records.json` は `sr-record.py` しか書けない。学習者に記録を頼む

## 送る前の自己チェック

最初の応答を送る前に、次の4つを確かめる。1つでも「いいえ」なら直してから送る。

- [ ] 「〜だから」と書いた理由はどれも、条件の違う類題（3と4で挙げたもの）でも成り立つか
- [ ] 学習者が次に「A？B？」「〜だから？」と聞き返しそうな箇所はないか。あれば先に答えたか
- [ ] 2つの用語を括弧・「＝」・「つまり」で同一視していないか
- [ ] 誤答と正答の数値を、両方とも実際に計算したか

## 長さについて

最初の応答は長くなってよい。何度も聞き直させるより、1回で読み切れるほうが学習者の時間を使わない。ただし見出しで区切り、各節は表か箇条書きで短くする。8節すべてを毎回同じ重さで書く必要はない。誤答の原因に関係しない節は1行で済ませる。

## 作ったあと

- 学習者が分析に食い違いを見つけたら（例：AI の説明の誤り）、weak_points.md の該当パターンに「AI 解説の誤り（学習者の誤答ではない）」として分けて書く
- 学習内容（`mistakes/` など）を変える PR を作るときは、CLAUDE.md の確認ルール（マージ前のクイズ）に従う
